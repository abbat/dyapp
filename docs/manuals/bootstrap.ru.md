# Руководство оператора bootstrap-узла

Это руководство ведёт оператора от пустого хоста Debian 12 до работающего bootstrap-узла `dyappd`
и через его повседневную эксплуатацию. Это перевод английского оригинала той же ревизии,
[bootstrap.md](bootstrap.md); при расхождении верен оригинал. Как узел устроен внутри, описано в
[Bootstrap server architecture](../architecture/bootstrap.md); руководство ссылается туда, когда
параметру нужно больше абзаца.

> ⚠️ **Не готово к промышленной эксплуатации.** Клиенты на `rust/client` отправляют сообщения
> только как шифротекст MLS, дополненный до степени двойки от 1 КиБ, поэтому оператор видит
> размеры и время конвертов, но не текст; проверить, что клиент шифрует, узел не может. Узел
> проверяет подписи Ed25519: владельца на профилях, отправителя на
> конвертах и устройства на чтении почтового ящика. См.
> [Encryption & Security Status](../security/encryption.md) и [Privacy](../security/privacy.md).

## Что делает узел

`dyappd` — узел libp2p сети dyapp. Клиенты записывают в него профили, конверты почтовых ящиков и
медиа; он хранит их ограниченное время, реплицирует на другие узлы и отдаёт обратно. Узел
выполняет одну или несколько ролей:

| Роль | Обслуживает |
|------|-------------|
| `store` | Профили, почтовые ящики и каталог сети (Kademlia DHT). Базовая роль; она нужна и всем остальным ролям. |
| `media` | Медиаблобы: аватары и вложения чатов. |
| `turn` | Короткоживущие пароли для ретранслятора coturn, работающего рядом с узлом ([TURN-ретранслятор](#turn-ретранслятор)). Звонки не входят в первый выпуск. |
| `search` | Поиск профилей ([Search](../architecture/bootstrap.md#search)). Включена по умолчанию, чтобы в маленькой сети был поиск; держит индекс профилей всей сети, до `search.max_bytes` (50 ГиБ) диска. На маленьком диске уменьшите его или задайте `roles = ["store"]`. |

Каждая запись целиком реплицируется в пять точек DHT и подтверждается, когда её сохранили два
разных узла; медиа больше 1 МиБ разбиваются на шарды Рида — Соломона. Узлы сами восстанавливают
недостающие реплики друг у друга ([replication](../architecture/bootstrap.md#replication-and-repair)).
Одиночный узел хранит единственную копию, поэтому сети нужно несколько узлов.

## Требования

- Debian 12 (bookworm) с systemd или любой Linux-хост с Docker.
- Около 2 vCPU, 1 ГиБ памяти и 16 ГиБ диска при квотах по умолчанию ([Ёмкость](#ёмкость)).
  Работайте без swap: ключ не должен туда попасть.
- Публичный адрес IPv4 и/или IPv6, открытые TCP **и** UDP на порту узла (по умолчанию 33445).
- Аутентифицированный источник времени, например `chrony` с NTS ([Часы](#часы)).
- Необязательно: TPM 2.0 или vTPM, чтобы запечатанный ключ узла был привязан к машине
  ([Ключ узла](#ключ-узла)).

## Где взять dyappd

Тег `vX.Y.Z` публикует пакет, архив tar, SPDX SBOM и `SHA256SUMS` в GitHub Releases
`abbat/dyapp`, а образ — как `ghcr.io/abbat/dyappd:X.Y.Z`
([ADR 0020](../decisions/0020-dyappd-release-channels.md)). Каждый файл и образ несут подписанную
Sigstore аттестацию SLSA build provenance; проверьте её перед установкой
([supply chain](../security/threat-model.md#supply-chain)):

```bash
sha256sum -c SHA256SUMS
gh attestation verify dyappd_X.Y.Z_amd64.deb --repo abbat/dyapp
gh attestation verify oci://ghcr.io/abbat/dyappd:X.Y.Z --repo abbat/dyapp
```

Выпусков пока нет. До тех пор, или чтобы проверить выпуск, соберите пакет или образ сами из
коммита, которому доверяете:

```bash
git clone https://github.com/abbat/dyapp && cd dyapp
make deb      # → build/deb/dyappd_<version>_<arch>.deb и архив tar, собираются в Debian 12
make image    # → образ контейнера dyappd:latest
```

`make deb` собирает release-бинарник в образе Debian 12, поэтому он работает на glibc 2.36, и
пробно устанавливает пакет и [архив tar](#архив-tar-ручная-установка) в чистый
`debian:bookworm-slim`. `make image` запускает образ в режиме
только для чтения без сети, создаёт ключ, запускает узел, меняет список запретов и проверяет, что в
образе нет оболочки. Обоим нужен только Docker на хосте сборки.

**Список зависимостей в бинарнике.** Обе сборки используют `cargo auditable build`: бинарник несёт
имена и версии своих crate в виде сжатого zlib JSON в ELF-секции `.dep-v0`, которую `strip`
сохраняет. `tools/scripts/check-auditable.py` проверяет, что список называет `dyapp-bootstrap` и совпадает
с `Cargo.lock`. Чтобы проверить установленный бинарник по RustSec, выполните
`cargo audit bin /usr/bin/dyappd` (cargo-audit) или извлеките список через `rust-audit-info`.
Список называет скомпилированные crate; это не SPDX SBOM, и он ничего не говорит о том, достижим
ли код из бюллетеня.

## Установка

### Пакет Debian 12

```bash
sudo apt install ./dyappd_*.deb        # создаёт пользователя dyappd, включает unit
```

Пакет содержит `/usr/bin/dyappd`, `/etc/dyappd.toml` (conffile, сохраняется при обновлении) и
`/lib/systemd/system/dyappd.service`. Unit:

- работает от системного пользователя `dyappd` (без оболочки и входа) без capabilities, с
  `NoNewPrivileges`, системой только для чтения (`ProtectSystem=strict`), без доступа к `/home`, с
  отдельным `/tmp` и правом записи только в `/var/lib/dyappd`;
- ограничен `MemoryHigh=768M`, `MemoryMax=1G`, `CPUQuota=150%` и `TasksMax=256`;
  `limits.max_memory_mb` по умолчанию равен MemoryHigh, поэтому узел сбрасывает запросы раньше,
  чем ядро начнёт его тормозить. На большем хосте поднимите оба значения в drop-in;
- задаёт `LimitCORE=0` и `MemorySwapMax=0` (cgroup v2); `dyappd` также при запуске делает себя
  недампируемым, так что ключ узла не попадает в core dump и swap;
- расшифровывает [запечатанный ключ узла](#ключ-узла) через `LoadCredentialEncrypted=node.key`;
- пишет журнал в journal с `RUST_LOG=info`; `systemctl reload dyappd` посылает SIGHUP.

Порт по умолчанию 33445 не требует привилегий; подходит любой порт, seeds и клиенты его
указывают, а сама смена порта не скрывает трафик от DPI
([почему 33445](../architecture/bootstrap.md#default-port)). Явно заданный адрес с портом 7070
продолжает работать; при переносе узла обновите правила межсетевого экрана и список seed-узлов.
Другой `storage.dir` или порт ниже 1024 требует drop-in (`sudo systemctl edit dyappd`):

```ini
[Service]
ReadWritePaths=/srv/dyappd
# Только для порта ниже 1024:
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
```

Удаление пакета останавливает и отключает unit. Полное удаление (`apt purge dyappd`) оставляет
пользователя, `/var/lib/dyappd` и `/etc/credstore.encrypted/node.key`, потому что ключ — это
личность узла: удалите их вручную, чтобы [вывести узел из работы](#вывод-узла-из-работы).

### Образ контейнера

```bash
docker volume create dyappd
run="docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges:true -v dyappd:/var/lib/dyappd"
$run dyappd:latest keygen              # один раз: около минуты на 2 vCPU
$run -d --name dyappd --memory 1g -p 33445:33445/tcp -p 33445:33445/udp \
    -e DYAPPD_SEEDS='["seed.example.org:33445"]' dyappd:latest
docker exec dyappd dyappd deny add <entry> [note]   # применяется в течение 10 с
docker exec dyappd dyappd status
docker logs dyappd
```

`tools/docker/Dockerfile.dyappd` копирует release-бинарник вместе с библиотеками glibc, с которыми он
связан, на пустую основу: без оболочки, без менеджера пакетов, без `/etc`. Узел работает с UID
65532 и пишет только в `/var/lib/dyappd` — свой `storage.dir` и единственный том образа, поэтому
корень может быть только для чтения, а все capabilities сброшены. Новый именованный том получает
владельца и режим 0700 из образа; bind mount требует `chown 65532:65532`. Образ задаёт `listen`
равным `["[::]:33445", "0.0.0.0:33445"]`; остальные настройки — переменные `DYAPPD_`, опции
`--<section>.<key>` после имени образа или файл настроек, смонтированный только для чтения в
`/etc/dyappd.toml`: он читается без `--config`. С `--memory 1g` значение по умолчанию
`limits.max_memory_mb = 768` сбрасывает запросы раньше предела Docker. В контейнере
ключ — обычный файл 0600 в томе.

Образ не опубликован в реестре, манифестов Kubernetes пока нет.

### Архив tar (ручная установка)

Для хоста без `apt` или оператора, который хочет видеть каждый шаг: `make deb` также пишет
`build/deb/dyappd-<version>-<machine>-linux-gnu.tar.gz` с тем же бинарником (glibc 2.36 или
новее), `dyappd.toml`, `LICENSE` и `dyappd.service` — юнитом пакета с бинарником в
`/usr/local/bin/dyappd`. Это gzip, а не xz: `tar -xzf` есть везде, а архив в любом случае весит
несколько мегабайт. `make deb` устанавливает его так в чистый Debian 12:

```bash
tar -xzf dyappd-*-linux-gnu.tar.gz && cd dyappd-*-linux-gnu
sudo install -m 0755 dyappd /usr/local/bin/dyappd
sudo install -m 0644 dyappd.toml /etc/dyappd.toml
sudo install -m 0644 dyappd.service /etc/systemd/system/dyappd.service
sudo useradd --system --user-group --home-dir /var/lib/dyappd --shell /usr/sbin/nologin dyappd
sudo install -d -o dyappd -g dyappd -m 0750 /var/lib/dyappd
sudo systemctl daemon-reload
```

Затем создайте и запечатайте ключ ([Ключ узла](#ключ-узла)), задайте `listen` в
`/etc/dyappd.toml` ([Настройка](#настройка)) и запустите: `sudo systemctl enable --now dyappd`;
`sudo -u dyappd dyappd status` печатает `node running`. Юнит тот же, что в пакете, с той же
песочницей и пределами, поэтому остальная часть руководства применима как есть.

Это системный юнит с `User=dyappd`, а не юнит `systemd --user`: пользовательский менеджер
работает, только пока пользователь вошёл в систему (если не включён lingering), и не может ни
применить системную песочницу выше, ни расшифровать credential, запечатанный ключом хоста. Без
systemd запускайте `dyappd --config /etc/dyappd.toml` от имени `dyappd` под своим супервизором с
ключом в файле 0600 (`storage.key`); `dyappd status` завершается с 0, пока узел отвечает, и с 3,
когда нет.

Для обновления сохраните старый бинарник
(`sudo cp -f /usr/local/bin/dyappd /usr/local/bin/dyappd.previous`), установите новый бинарник и
новый юнит, сравните `dyappd.toml` со своим `/etc/dyappd.toml`, затем
`sudo systemctl daemon-reload && sudo systemctl restart dyappd` ([Обновления](#обновления)). Для
отката верните `dyappd.previous` и перезапустите ([Откат](#откат)). Для удаления отключите юнит и
удалите три установленных файла; пользователь, `/var/lib/dyappd` и запечатанный ключ остаются, как
и с пакетом.

## Ключ узла

Ключ узла — ключ Ed25519 libp2p. Его peer ID — личность узла: пиры закрепляют его, хранилища
привязаны к нему, а новый ключ — это новый узел. Ключ несёт доказательство работы: SHA-256 от
peer ID начинается с `network.id_pow_bits` нулевых бит (22 в публичной сети, около минуты на
2 vCPU; [ADR 0008](../decisions/0008-sybil-and-eclipse-defences.md)).

`dyappd` читает ключ из файла, и ему всё равно, как хост его защищает. При пустом `storage.key`
он берёт `$CREDENTIALS_DIRECTORY/node.key`, когда unit передаёт такой credential, иначе
`storage.dir/node.key`; заданный `storage.key` всегда главнее.

**Запечатанный через systemd-creds (по умолчанию в пакете).** Открытый ключ никогда не касается
диска:

```bash
sudo install -d -m 0700 /etc/credstore.encrypted
sudo -u dyappd dyappd keygen - |   # печатает peer ID в stderr
  sudo systemd-creds encrypt --with-key=auto --name=node.key - /etc/credstore.encrypted/node.key
```

`LoadCredentialEncrypted=node.key` в unit находит файл по имени и расшифровывает его в каталог в
памяти, который читает только служба. `--with-key=auto` привязывает credential к TPM 2.0 и к
ключу хоста в `/var/lib/systemd/credential.secret`, если TPM есть (`systemd-creds has-tpm2`), так
что одна лишь копия диска его не открывает. Без TPM используется только ключ хоста, лежащий на
том же диске: это защищает от случайной копии файла ключа, но не от скопированного тома.

**Проверка TPM.** Наличие устройства TPM на хосте ещё не значит, что ключ к нему привязан;
проверьте каждый шаг:

| Шаг | Команда | Ожидается |
|-----|---------|-----------|
| 1. Устройство доступно | `ls -l /dev/tpmrm0` | Файл есть. Если нет: на железе включите TPM 2.0 в прошивке; на ВМ включите vTPM провайдера (например, GCP Shielded VM, Azure Trusted Launch, AWS NitroTPM), часто для этого нужна новая ВМ. В контейнер TPM не попадает: там ключ — обычный файл 0600. |
| 2. systemd может его использовать | `systemd-creds has-tpm2` | `yes` и код выхода 0. `partial` называет недостающую часть (`-firmware`, `-driver`, `-system`). |
| 3. Запечатать на него | `--with-key=host+tpm2` вместо `--with-key=auto` в команде keygen выше | Команда успешна. В отличие от `auto`, она завершается ошибкой, а не откатывается к одному ключу хоста. |
| 4. Узел его открывает | `sudo systemctl restart dyappd`, затем `sudo -u dyappd dyappd status` | `node running`. Credential, привязанный к изменённому или очищенному TPM, не расшифровывается, и unit не запускается. |

Без TPM (шаг 1 или 2 не прошёл) запечатывайте с `--with-key=host`: ключ всё равно не лежит
открытым текстом, но любой с копией всего диска его откроет. Если это важно, используйте пароль
или зашифрованный том (ниже). Сброс TPM или переезд на другую ВМ делают запечатанный ключ
нечитаемым: храните зашифрованную резервную копию из следующего абзаца.

**Запасная копия.** Запечатанный ключ нельзя перенести на другой хост. Чтобы сохранить резервную
копию, зашифруйте копию для себя при генерации, например через `age`:

```bash
sudo -u dyappd dyappd keygen - | tee >(age -r <your age key> >node.key.age) |
  sudo systemd-creds encrypt --with-key=auto --name=node.key - /etc/credstore.encrypted/node.key
```

**Запечатывание старого открытого ключа.** Остановите узел, выполните
`sudo systemd-creds encrypt --with-key=auto --name=node.key /var/lib/dyappd/node.key /etc/credstore.encrypted/node.key`,
удалите открытый файл через `sudo shred -u /var/lib/dyappd/node.key` и запустите узел. Пока
существуют оба, используется credential.

**Без systemd или TPM** выберите одно:

- обычный файл 0600, `dyappd keygen` без `-` (контейнеры, тестовые узлы);
- пароль: храните ключ зашифрованным (`age -p`) и перед каждым запуском расшифровывайте его в файл
  0600 на `tmpfs`, указанный в `storage.key`;
- зашифрованный том (LUKS, открываемый Clevis/Tang или вручную) с `storage.dir`.

**Peer ID.** `sudo -u dyappd dyappd id` (в Docker: `docker exec dyappd dyappd id`) печатает
peer ID, затем по одной записи `seeds` на каждый адрес `external` — их можно сразу передать
операторам, которые добавят этот узел в свои seeds:

```text
12D3KooW...
[2001:db8::7]:33445/12D3KooW...
192.0.2.7:33445/12D3KooW...
```

Что проверяют keygen и запуск:

- `dyappd keygen` записывает ключ (режим 0600) в `storage.key` или `storage.dir/node.key`,
  записывает `node.id` (peer ID) и `network` (имя сети) в `storage.dir` и печатает peer ID;
  `dyappd keygen -` пишет ключ в stdout, отказывается писать в терминал и печатает peer ID в
  stderr.
- Keygen отказывается работать, если ключ или любые данные уже существуют.
- Узел не запускается без ключа, с ключом без доказательства работы или с ключом, не совпадающим с
  `node.id`.
- Файл ключа должен читаться только владельцем: запуск отклоняет биты прав группы и остальных с
  подсказкой `chmod 600` и сам режим не меняет; 0400 тоже загружается. Credential systemd не
  проверяется: systemd делает его читаемым только пользователю службы.

## Настройка

### Откуда берутся настройки

Каждая настройка необязательна. Поздние источники переопределяют ранние:

1. значения по умолчанию в коде;
2. TOML-файл, указанный через `--config`, иначе первый существующий из `./dyappd.toml`,
   `~/dyappd.toml` и `/etc/dyappd.toml` (`/etc/dyappd.toml` в пакете, каждый ключ закомментирован
   со своим значением по умолчанию, в репозитории это
   [`rust/bootstrap/dyappd.toml`](../../rust/bootstrap/dyappd.toml); тест держит этот файл
   равным коду);
3. переменные окружения `DYAPPD_<SECTION>_<KEY>`, разбираемые как TOML (голая строка берётся как
   есть), например `DYAPPD_LIMITS_MESSAGE_TTL_HOURS=48` или
   `DYAPPD_LISTEN='["[2001:db8::7]:33445"]'`;
4. опции `--<section>.<key>` с `-` вместо `_`, например `--limits.max-connections 500` или
   `--storage.dir=/srv/dyappd`; опция-список задаётся по разу на элемент и заменяет список
   (`--listen '[::]:33445' --listen 0.0.0.0:33445`).

`dyappd --help` перечисляет каждую опцию с её значением по умолчанию. При русской локали
(`LC_ALL`, затем `LC_MESSAGES`, затем `LANG`) названия команд остаются прежними, а справка о
командах и порядке чтения конфигурации выводится по-русски. Описания отдельных параметров
пока остаются на английском; их перевод запланирован до выпуска v0.0.1. Неизвестная опция
останавливает узел; неизвестный ключ в файле или окружении записывается в журнал и игнорируется,
так что конфигурация, написанная для более нового узла, не останавливает старый. Изменения
вступают в силу после перезапуска (`sudo systemctl restart dyappd`); на ходу перечитывается только
список запретов. Не передавайте `turn.secret` в командной строке: другие пользователи видят его в
`ps`.

При запуске узел отказывается работать от root, проверяет адреса, роли и лимиты по диапазонам
ниже, создаёт недостающие каталоги и проверяет, что каждый доступен на запись. Команды, кроме
`keygen`, нужно запускать от владельца `storage.dir` (`sudo -u dyappd dyappd ...`).

### Адреса и роли

| Ключ | По умолчанию | Значение |
|------|--------------|----------|
| `listen` | `["[::1]:33445", "127.0.0.1:33445"]` | Адреса, на которых слушает узел. По умолчанию только loopback, так что свежая установка никого не обслуживает; обслуживающий узел задаёт `["[::]:33445", "0.0.0.0:33445"]`. Сокеты IPv6 только для IPv6, поэтому узел с двумя стеками перечисляет оба. Каждый адрес обслуживает TCP и QUIC (UDP) на своём порту. Адрес, который не открылся, записывается как `not listening` и пропускается; узел завершается, только если не открылся ни один. |
| `external` | `[]` | Публичные адреса, объявляемые пирам, если они известны (статический адрес, проброс порта). Пусто: пиры узнают адреса прослушивания через identify (только глобальные, если они есть), а адрес, с которого они видят узел, объявляется, когда его подтвердит AutoNAT. До тех пор узел — клиент DHT: пользуется DHT, но не обслуживает её часть. |
| `seeds` | `[]` | Узлы для входа в сеть: `host:port` или `host:port/<peer ID>`, где host — IP или DNS-имя (например `seed.example.org:33445`, `[2001:db8::7]:33445`). Peer ID, который печатает `dyappd id` seed-узла, закрепляет ключ seed-узла: другой ключ отклоняется с записью в журнал уровня warn. Имя с несколькими записями A/AAAA перебирается по адресам. Без закрепления тот, кто контролирует имя или хост, контролирует первых пиров. Последующие запуски также подключаются к пирам, сохранённым в `storage.dir`, так что seeds — только способ войти. Мультиадреса libp2p отклоняются. |
| `roles` | `["store", "search"]` | Любые из `store`, `media`, `turn`, `search` ([Что делает узел](#что-делает-узел)). Каждая роль, кроме store, отклоняется при запуске, если `store` нет в списке. Узел без роли отвечает на её запросы `UNSUPPORTED`. |

`listen` и `external` принимают IP, а не имя хоста; адрес IPv6 пишется в квадратных скобках.

<a id="without-a-domain"></a>**Без домена.** Своего домена узлу не нужно. Запись в `seeds`
называет узел адресом или именем, а peer ID после `/` доказывает, что это ваш узел; имя только
помогает его найти. Выбирайте по тому, насколько стабилен адрес:

| Вариант | Пример записи в `seeds` | Плюсы | Минусы |
|---------|-------------------------|-------|--------|
| IP напрямую | `192.0.2.7:33445/12D3KooW...` | Без третьей стороны; нечего продлевать | При смене адреса каждый оператор, указавший узел, правит запись |
| Бесплатное имя динамического DNS | `mynode.duckdns.org:33445/12D3KooW...` | Запись переживает смену адреса; бесплатно | Сбой провайдера или потеря имени мешают новым узлам войти через этот seed; токен обновления нужно беречь |
| Свой домен | `seed1.example.org:33445/12D3KooW...` | Под вашим контролем; свой DNS-провайдер и TTL | Платный, нужно продлевать; истёкший домен теряется, как любое имя |

Бесплатные провайдеры динамического DNS, по их собственным страницам (октябрь 2026; условия
меняются, проверьте перед использованием):

| Провайдер | Бесплатных имён | IPv6 (AAAA) | Обновление |
|-----------|-----------------|-------------|------------|
| [Duck DNS](https://www.duckdns.org/spec.jsp) | несколько имён `*.duckdns.org` | Да, адрес указывается явно (не определяется сам) | HTTPS GET с токеном: `?domains=…&token=…&ip=…&ipv6=…` |
| [Dynu](https://www.dynu.com/FAQ/Dynamic-DNS-Service) | 4 имени | Да | Клиент обновления или HTTPS API |
| [FreeDNS (afraid.org)](https://freedns.afraid.org/faq/) | несколько поддоменов общих доменов | Да | URL обновления; связанные записи с одним IP обновляются вместе; TTL 60 с |
| [ClouDNS](https://www.cloudns.net/dynamic-dns/lang/en/) | 1 динамическое имя | Да | Отдельный URL обновления для каждой записи A или AAAA |

В seed с именем у третьей стороны всегда закрепляйте peer ID: владелец имени или аккаунта может
направить его куда угодно, а закреплённый ID превращает это из перехвата в отказ подключения.
Не кладите токен обновления в общие конфиги: украденный токен позволяет перенаправить имя, и
закреплённый ID снова сводит это к недоступности, а не к атаке. Указывайте больше одного seed,
лучше у разных провайдеров или с прямым IP, чтобы сбой одного провайдера или потерянное имя не
закрыли вход новым узлам. Провайдер видит, кто и когда запрашивает имя. Узел разрешает имя при
каждом подключении, поэтому новый адрес начинает использоваться после истечения TTL записи, а
работающий узел в любом случае хранит свой кэш пиров.

## Первый запуск

При установке пакетом, после [запечатывания ключа](#ключ-узла):

```bash
sudoedit /etc/dyappd.toml        # как минимум: listen, seeds (или external на известном адресе)
sudo systemctl start dyappd
journalctl -u dyappd -f          # "listening on ..." для каждого адреса
sudo -u dyappd dyappd status
```

Минимальная конфигурация обслуживающего узла:

```toml
listen = ["[::]:33445", "0.0.0.0:33445"]
seeds = ["seed1.example.org:33445/12D3KooW...", "seed2.example.org:33445/12D3KooW..."]
```

Откройте TCP и UDP на порту в межсетевых экранах хоста и облака. Проверьте с другого хоста через
`dyappd info` ([клиентские команды](../architecture/bootstrap.md#client-commands)):

```bash
dyappd info node.example.org:33445   # код 0 и "STATUS_OK" → жив
dyappd info [2001:db8::7]:33445      # адрес IPv6 — в квадратных скобках
dyappd info 192.0.2.7:33445          # адрес IPv4
```

Новый узел отвечает на записи `STATUS_FULL`, пока у него нет доверенных пиров в течение
`network.storage_trust_minutes`; чтение работает сразу.

### Первое развёртывание

Шаги ниже запускают сеть seed-узлов с промышленными значениями по умолчанию
(`id_pow_bits = 22`, `distinct_outbound_groups = true`, `storage_trust_minutes = 60`) и проводят её
через одно обновление и один откат.

Узел отправляет реплики только пирам, с которыми впервые соединился не менее
`network.storage_trust_minutes` назад, и хранит это время только в памяти. Записи (профилю,
конверту, части медиа) нужен второй хранитель, поэтому узел, ещё не доверяющий ни одному пиру,
через 10 секунд отвечает на неё `STATUS_FULL`; чтение не затрагивается. Поэтому новая сеть
отклоняет все записи в течение первого периода доверия, а каждый перезапущенный узел отклоняет их
в течение одного периода. Пиры перезапущенного узла продолжают ему доверять, пока он остаётся в
их таблице маршрутизации.

1. **Холодный старт.** Сгенерируйте каждый ключ (около минуты на узел при 22 битах), перечислите
   остальные seed-узлы в `seeds` на каждом и запустите их в любом порядке; к seed-узлу,
   стартовавшему первым, подключатся последующие. Проверьте каждый через `dyappd info`.
2. **Канарейка.** Через `storage_trust_minutes` опубликуйте тестовый профиль через каждый узел:
   `dyappd publish` возвращает `STATUS_OK`, а `dyappd get` находит запись как минимум на
   двух узлах. Раньше этого он возвращает `STATUS_FULL`.
3. **Поочерёдное обновление.** Для каждого узла по очереди: остановите его, сделайте
   [резервную копию](#резервные-копии) `storage.dir`, запустите новую версию, проверьте её
   работоспособность и то, что она всё ещё отдаёт записи-канарейки, опубликуйте канарейку через
   узел, который не перезапускался в последний период доверия, затем подождите
   `storage_trust_minutes` перед следующим узлом. Перезапуск всех узлов в пределах одного периода
   останавливает все записи, пока не кончится период первого перезапущенного узла.
4. **Откат.** Остановите узел и запустите старую версию. Если обновление изменило формат
   хранилища, старая версия завершается с "has store format N, this dyappd knows up to M";
   восстановите копию из шага 3 и запустите на ней старую версию. Записи, принятые узлом после
   копии, на этом узле теряются; их восстанавливают другие реплики и следующий визит владельца.
   Отката через смену формата хранилища без этой копии нет.

`make rehearsal FROM=<git ref>` выполняет эти шаги на трёх loopback-узлах (127.1.0.1, 127.2.0.1 и
127.3.0.1, три группы /16) с release-сборками ref и рабочего дерева, где ref — коммит до смены
формата хранилища; это занимает около трёх периодов доверия (`tests/scripts/rehearsal.py`). Ручной
workflow `rehearsal.yml` выполняет ту же проверку на CI с ref во входе `from`.

## Состояние и метрики

**Состояние.** `sudo -u dyappd dyappd status` (в Docker:
`docker exec dyappd dyappd status`) печатает по строке `имя значение`, сначала самое важное:

| Строка | Значение |
|---|---|
| `node` | `running`, когда узел отвечает на `info` по адресу из `listen` (хост `[::]` или `0.0.0.0` набирается через loopback, не дольше 15 с), иначе `stopped` |
| `peer_id` | peer ID узла, пусто до `keygen` |
| `profiles`, `envelopes`, `media_blobs`, `deny_entries` | число записей; `none`, если хранилище ещё не создано |
| `purged_blobs` | сколько медиаблобов удалено по списку запретов за всё время; `none`, если хранилище медиа ещё не создано |
| `envelope_bytes`, `media_bytes` | хранимые байты; `none` так же |
| `cached_peers` | пиры, сохранённые для следующего запуска |
| `uptime_seconds`, `requests`, `wire_in_bytes`, `wire_out_bytes` | секунды с запуска узла, затем запросы и байты полезной нагрузки, принятые и отправленные по всем протоколам с того же момента, из слушателя [метрик](#метрики); `unavailable`, когда узел остановлен, `[metrics] port` равен 0 или слушатель не отвечает |

Код выхода 0, когда узел работает, и 3 (код LSB «не запущен»), когда нет, так что
`dyappd status >/dev/null || alert` работает без systemd. Команда открывает хранилища только
для чтения, не делает ничего дороже подсчётов SQLite и работает при запущенном узле. HTTP API
администрирования нет.

**Журнал.** `journalctl -u dyappd` (при ручном запуске — stderr). Узел пишет запуск, адреса
прослушивания, ошибки хранилища, ежечасную очистку и обслуживание, но не отдельные запросы.
`RUST_LOG` задаёт уровень, например `RUST_LOG=info` (по умолчанию в unit) или `RUST_LOG=debug`.
`sudo systemctl reload dyappd` (SIGHUP) пишет одну строку состояния в памяти: ожидающие запросы,
число соединений и пиров.

**Работоспособность.** HTTP-эндпоинта проверки нет. Узел жив, когда отвечает на `/dyapp/node`
`info` (`dyappd info`, выше; `dyappd status` проверяет это локально); ответ содержит только
роли и лимиты.

### Метрики

Задайте `[metrics] port = 9464`, чтобы отдавать текст Prometheus по
`http://[::1]:9464/metrics` и, для инструментов только с IPv4, по
`http://127.0.0.1:9464/metrics`. Сборщик на другом хосте достигает его через туннель или локальный
агент. Семейства и ограничения слушателя:
[metric families](../architecture/bootstrap.md#metric-families),
[metrics listener](../architecture/bootstrap.md#metrics-listener).

```bash
curl -s 'http://[::1]:9464/metrics' | grep '^dyapp_connected_peers'
```

Как читать значения:

- Счётчики (`*_total`) начинаются с 0 вместе с процессом. Перезапуск виден как новый
  `dyapp_process_start_time_seconds`; используйте `rate()`/`increase()` в Prometheus или шаг
  "Change per second" в Zabbix — оба считают падение сбросом.
- Датчики хранилища устаревают до 5 минут: оповещайте по
  `time() - dyapp_snapshot_timestamp_seconds > 900` (нет снимка три периода) и по
  `dyapp_storage_read_ok == 0`, а не по отсутствию `storage_used_bytes`.
- Набор рядов определяется ролями и настроенными хранилищами.

**Prometheus.** Запустите Prometheus или пересылающий в него агент на хосте узла:

```yaml
scrape_configs:
  - job_name: dyappd
    scrape_interval: 60s
    scrape_timeout: 4s     # меньше 5-секундного срока слушателя
    static_configs:
      - targets: ['[::1]:9464']
```

**Zabbix.** Один главный элемент данных забирает страницу, а зависимые элементы вырезают из неё
значения шагом предобработки "Prometheus pattern", так что каждый сбор — один запрос:

- Главный элемент, тип "HTTP agent", URL `http://[::1]:9464/metrics`, тип информации "Text",
  история 0. HTTP agent работает на сервере или прокси Zabbix, поэтому нужен один из них на хосте
  узла. Иначе используйте как главный элемент Zabbix agent
  `web.page.get[127.0.0.1,/metrics,9464]`; он возвращает и заголовки ответа, поэтому добавьте
  первым шагом "Regular expression" `\r\n\r\n([\s\S]*)` с выводом `\1`.
- Зависимые элементы с главным элементом выше и предобработкой "Prometheus pattern", например
  `dyapp_connected_peers` (числовой беззнаковый) или
  `dyapp_request_outcomes_total{protocol="mailbox",outcome="omitted"}` с последующим
  "Change per second".

Ни одна из этих настроек не устанавливается и не тестируется проектом; сам формат вывода
проверяется модульными тестами `metrics`.

## Эксплуатация

### Изменение настроек

Отредактируйте `/etc/dyappd.toml` (или `Environment=` в drop-in) и выполните
`sudo systemctl restart dyappd`. Перезапуск заставляет узел отклонять записи в течение
`storage_trust_minutes`; в сети из нескольких узлов перезапускайте их по одному, как при
[поочерёдном обновлении](#обновления).

### Обновления

Установите новый пакет (`sudo apt install ./dyappd_<new>.deb`) или запустите новый образ, по
одному узлу за раз:

- У профилей, почтовых ящиков и медиа пять реплик на других узлах, поэтому пока один узел
  недоступен, клиенты читают другие реплики, а следующий визит владельца восстанавливает
  пропущенное. Одиночный узел хранит единственную копию.
- Перезапущенный узел не доверяет ни одному пиру в течение `network.storage_trust_minutes` и всё
  это время отклоняет записи; перезапускайте следующий узел только после этого
  ([Первое развёртывание](#первое-развёртывание)).
- При запуске новый `dyappd` обновляет файлы хранилища на месте (каждый хранит свой формат в
  `PRAGMA user_version`). Старый `dyappd` отклоняет файлы, обновлённые новым, поэтому для отката
  нужна [резервная копия](#резервные-копии), сделанная до обновления. Построение изменённого
  формата рядом со старым, пока старый продолжает отвечать, запланировано.
- `apt` сохраняет ваш отредактированный `/etc/dyappd.toml`; сравните его с новым значением по
  умолчанию в `/etc/dyappd.toml.dpkg-dist`, если `apt` его предложит.

### Откат

Остановите узел, установите предыдущий пакет и запустите его. Если он завершается с "has store
format N, this dyappd knows up to M", остановите его, восстановите копию, сделанную до
обновления, и запустите снова ([Первое развёртывание](#первое-развёртывание), шаг 4).

### Список запретов

Чтобы перестать обслуживать нарушителя или медиаблоб, добавьте его peer ID, IP-группу, хеш ключа
или SHA-256 блоба:

```bash
sudo -u dyappd dyappd deny add <entry> [note]
sudo -u dyappd dyappd deny remove <entry>
sudo -u dyappd dyappd deny list
```

Работающий узел применяет изменение в течение 10 секунд или сразу по `systemctl reload dyappd`;
запрещённые пиры получают здесь `STATUS_REFUSED` и пользуются другими узлами. IP-группа задаётся с
префиксом узла, например `198.51.100.0/24`. После обновления списка узел удаляет локальную
копию блоба, манифест и фрагменты. Записи keep и вложений остаются, но блоб считается
отсутствующим. Узел записывает хеш в журнал и увеличивает счётчик `purged_blobs` в выводе
`dyappd status`. Удаление записи из списка не восстанавливает блоб; владелец сможет загрузить
его заново. Список локален для узла и хранится в `deny.db`. Обмен
списками запретов между узлами (`share_deny_list`, `accept_deny_lists`) не входит в первый
выпуск: общий список сообщает другим операторам, что вы отклоняете, а полученные списки только
сохраняются для просмотра через `dyappd deny received`. Подробнее:
[deny list](../architecture/bootstrap.md#deny-list).

### Вывод узла из работы

```bash
sudo apt purge dyappd
sudo rm -rf /var/lib/dyappd /etc/credstore.encrypted/node.key
sudo userdel dyappd
```

Попросите операторов, у которых этот узел указан в `seeds`, убрать его. Его реплики
восстанавливаются с других хранителей.

### Компрометация ключа узла

Скопированный `node.key` нельзя отозвать, поэтому узел начинает заново как новый узел:

```bash
sudo systemctl stop dyappd
sudo rm -rf /var/lib/dyappd/*   # storage.dir: node.key, node.id и все хранилища
sudo rm -f /etc/credstore.encrypted/node.key   # запечатанный ключ, если используется
sudo -u dyappd dyappd keygen - |   # печатает новый peer ID
  sudo systemd-creds encrypt --with-key=auto --name=node.key - /etc/credstore.encrypted/node.key
sudo systemctl start dyappd
```

Keygen отказывается работать, пока остались данные, поэтому сначала очистка. Последствия:

- У узла новый peer ID. Украденным ключом всё ещё можно запустить узел под старым, поэтому
  попросите операторов, у которых указан старый ID (seed `host:port/<peer ID>`, запись запрета),
  заменить его или запретить через `dyappd deny add <old peer ID>`.
- То, что хранил старый узел, для него потеряно; репликация восстанавливает профили, почтовые
  ящики и медиа с других хранителей, а одиночный узел теряет единственную копию.
- Обновите свои seeds и всё остальное, что закрепляет старый ID.

### TURN-ретранслятор

Роль `turn` выдаёт учётные данные для ретранслятора coturn, работающего рядом с узлом; сам
`dyappd` ничего не ретранслирует. Звонки не входят в первый выпуск. Установите coturn
(`apt-get install coturn` в Debian 12) и задайте в `/etc/turnserver.conf`:

```
use-auth-secret
static-auth-secret=<the same secret as turn.secret>
realm=turn.example.org
total-quota=100
user-quota=4
max-bps=1000000
no-multicast-peers
no-tcp-relay
denied-peer-ip=0.0.0.0-0.255.255.255
denied-peer-ip=10.0.0.0-10.255.255.255
denied-peer-ip=100.64.0.0-100.127.255.255
denied-peer-ip=127.0.0.0-127.255.255.255
denied-peer-ip=169.254.0.0-169.254.255.255
denied-peer-ip=172.16.0.0-172.31.255.255
denied-peer-ip=192.0.0.0-192.0.0.255
denied-peer-ip=192.168.0.0-192.168.255.255
denied-peer-ip=198.18.0.0-198.19.255.255
denied-peer-ip=240.0.0.0-255.255.255.255
denied-peer-ip=::1
denied-peer-ip=fc00::-fdff:ffff:ffff:ffff:ffff:ffff:ffff:ffff
denied-peer-ip=fe80::-febf:ffff:ffff:ffff:ffff:ffff:ffff:ffff
denied-peer-ip=64:ff9b::-64:ff9b::ffff:ffff
no-cli
```

Диапазоны `denied-peer-ip`, `no-multicast-peers` и `no-tcp-relay` не дают пиру с учётными
данными ретранслировать в собственную сеть оператора или к метаданным облака; coturn принимает
здесь отдельные адреса или диапазоны `a-b`, не CIDR. Ретрансляция на публичные адреса остаётся
возможной, её ограничивают квоты.

Подбирайте квоты по исходящему каналу ретранслятора. `max-bps` ограничивает каждую сессию в байтах
в секунду (1000000 — около 8 Мбит/с); `user-quota` ограничивает одновременные выделения одного
имени пользователя, то есть одних учётных данных одного пира; `total-quota` ограничивает все
выделения, поэтому ставьте его примерно равным каналу, делённому на `max-bps`. Пример рассчитан
на канал 1 Гбит/с с запасом.

Передавайте секрет файлом через `turn.secret_file` (или `DYAPPD_TURN_SECRET` через systemd
`EnvironmentFile=` с режимом 0600). Откройте порт
прослушивания (3478 UDP и TCP, 5349 для TLS) и диапазон портов ретрансляции
(`min-port`/`max-port`, по умолчанию 49152–65535). При запуске узел отклоняет роль без секрета или
с URL, который не начинается с `turn:` или `turns:`. Учётные данные истекают через
`turn.credential_minutes`; смена секрета требует одновременного перезапуска обеих служб.

### Очистка и уплотнение данных

Просроченные конверты, профили, tombstone и вложения удаляются каждый час по
[срокам хранения](#limits). Полный `VACUUM` не нужен: каждые `maintenance.interval_minutes` узел
возвращает файловой системе до `maintenance.vacuum_pages` свободных страниц на хранилище
(`profiles.db`, `messages.db` и поисковый индекс), усекает WAL и обновляет статистику
планировщика. Строки журнала "store maintenance done" и "search index maintenance done"
показывают оставшиеся свободные страницы; постоянно растущее число значит, что `vacuum_pages`
мало для скорости удаления. Фоновые перестройки делят `maintenance.io_mb_per_s` и сообщают
"store rebuild progress".

## Резервные копии

Горячего резервного копирования нет: файлы SQLite, скопированные во время записи, несогласованы.
Сначала остановите узел.

| В `storage.dir` | Копировать? |
|-----------------|-------------|
| `node.key` (если не запечатан и не задан через `storage.key`) | **Да**, приватно: потерянный ключ — это новый узел. Запечатанный ключ копируется как копия `age`, сделанная при keygen. |
| `node.id`, `network` | Да: без них узел не запускается на своих хранилищах. |
| `profiles.db`, `messages.db`, `media.db` и `data/` | Да перед обновлением (единственный путь назад через смену формата хранилища); иначе необязательно, так как реплики восстанавливаются с других узлов. |
| `deny.db` | Да: ваш список запретов. |
| `profiles-idx.db` или `profiles-idx-vN.db`, `search.lock` | Нет: поисковый индекс одноразовый и заново наполняется догоняющей синхронизацией. |
| `peers`, `anchors` | Нет: кеш пиров, восстанавливается из сети. |

Файл `traffic`, оставшийся от старой версии, больше не читается и может быть удалён. Пример для
раскладки пакета:

```bash
sudo systemctl stop dyappd
sudo sh -c 'umask 077; tar czf /root/dyappd-$(date +%Y%m%d).tar.gz -C /var/lib dyappd'
sudo systemctl start dyappd
# Восстановление: остановить, убрать /var/lib/dyappd в сторону, распаковать в /var/lib, запустить, проверить status
```

Храните копии с `node.key` вне облачного провайдера или зашифрованными ключом, которого у него
нет. Резервное копирование по расписанию, ротация и хранение вне хоста не предоставляются.

## Безопасность

### Сеть

Каждое соединение — libp2p: TCP с Noise и yamux или QUIC (TLS 1.3), аутентифицированное ключом
узла; удостоверяющего центра нет. Протокол узла публичный: любой может прочитать любой профиль, а
сохранить, заменить или удалить его может только подпись владельца. Запросы ограничены на пира,
на IP-группу и на ключ отправителя, а пиры, которые постоянно упираются в лимиты или присылают
неверные подписи, локально банятся на `ban_minutes`.

### Часы

Сроки хранения, истечение и 10-минутные окна для подписанного времени используют часы узла. Часы,
сдвинутые вперёд, например поддельным NTP-сервером, заставляют ежечасную очистку удалить
конверты, профили и вложения раньше времени; сдвинутые назад — отклонять свежие heartbeat и keep.
Синхронизируйте хост с аутентифицированным источником и следите за большими скачками в журнале
`chrony`.

Ответы обычного NTP не подписаны: любой на пути между хостом и сервером времени может их
подделать и сдвинуть часы. Network Time Security (NTS, RFC 8915) добавляет TLS-рукопожатие с
сервером (NTS-KE, TCP-порт 4460): оно проверяет сертификат сервера и выдаёт ключи, и каждый
следующий ответ NTP (UDP-порт 123) несёт метку аутентификации, сделанную этими ключами. Тогда
`chrony` принимает только ответы, которые действительно пришли от этого сервера и не изменены по
дороге.

Сам по себе NTS не делает время верным. Выбранный сервер всё ещё может прислать неверное время,
хост виртуальной машины и любой с root на нём всё ещё могут перевести часы, а обычный источник
NTP рядом с NTS-источниками всё ещё может увести часы, если неаутентифицированные источники не
запрещены. Лучше взять два-три NTS-сервера разных операторов. В Debian 12 есть `chrony` 4.3 с
поддержкой NTS:

```bash
sudo apt-get install -y chrony
# Закомментируйте строку `pool` по умолчанию в /etc/chrony/chrony.conf, затем:
sudo tee /etc/chrony/sources.d/nts.sources >/dev/null <<'EOF'
server time.cloudflare.com iburst nts
server nts.netnod.se iburst nts
server ptbtime1.ptb.de iburst nts
EOF
echo 'authselectmode require' | sudo tee /etc/chrony/conf.d/nts.conf
sudo systemctl restart chrony
chronyc -N authdata   # у каждого сервера: Mode NTS, ненулевые KeyID и Cook
chronyc sources       # `^*` отмечает используемый сервер
chronyc tracking      # "Leap status: Normal" и малое смещение "System time"
```

`authselectmode require` заставляет `chrony` игнорировать все источники без аутентификации.
Межсетевой экран должен пропускать исходящие TCP 4460 и UDP 123. Если `authdata` показывает `-`
в Mode или ноль cookies, рукопожатие NTS не удалось: проверьте, что порт 4460 открыт и имя
сервера указано верно.

### Облачный хостинг

На арендованной ВМ исходите из того, что провайдер или любой, у кого есть ваш облачный аккаунт,
может читать диск, его снимки и копии, писать на диск и читать память ВМ. Тогда он может
скопировать ключ узла и секрет TURN, видеть то же, что видите вы как оператор, и заменить
`dyappd` сборкой с закладкой; подделать подписанные записи пользователей или прочитать сквозное
содержимое он не может ([threat model](../security/threat-model.md#cloud-host-access)).
Запечатанный ключ, привязанный к vTPM, не даёт получить ключ узла из скопированного тома; только
конфиденциальная ВМ (AMD SEV-SNP, Intel TDX) скрывает память работающей ВМ от хоста. Шифрования
хранилищ на диске и проверки целостности при запуске нет, поэтому:

- Защитите облачный аккаунт 2FA с аппаратным ключом и ограничьте, кто может делать снимки и
  подключать тома.
- Храните копии с ключом вне провайдера или зашифрованными ключом, которого у него нет.
- При подозрении на доступ переустановите из пакета, который вы собрали или проверили сами,
  выполните [Компрометация ключа узла](#компрометация-ключа-узла) и смените секрет
  [TURN](#turn-ретранслятор).

### Рекомендации

- Закрепляйте каждый seed его peer ID (`host:port/<peer ID>`).
- Сохраняйте промышленные значения по умолчанию `[network]` в публичной сети.
- Запускайте несколько узлов в разных /16 и у разных провайдеров; перезапускайте по одному.
- Держите слушатель метрик на loopback и собирайте его локально.
- Следите за свободным местом на диске, `dyapp_storage_read_ok` и возрастом снимка.
- Делайте резервную копию остановленного узла перед каждым обновлением.

## Ёмкость

Не измерена: нагрузочного теста пока нет. Диск, скорость в байтах, память и соединения
ограничены `[limits]`. При квотах по умолчанию узлу нужно около 16 ГиБ диска (`profiles_max_mb`
1 ГиБ + `messages_max_mb` 4 ГиБ + `media_max_mb` 10 ГиБ + `min_free_mb` 512 МиБ; без роли media
около 6 ГиБ; роль search по умолчанию добавляет по мере роста сети до `search.max_bytes`,
50 ГиБ, поэтому на маленьком диске уменьшите его) и 1 ГиБ памяти (`MemoryMax=1G`,
`limits.max_memory_mb` 768). Заполненное хранилище отвечает `FULL`, а не растёт.

## Устранение неполадок

| Симптом | Что проверить |
|---------|---------------|
| `dyappd info` падает по таймауту или с `request failed` | Узел не работает, адрес неверен (`хост:порт`, адрес IPv6 — в квадратных скобках) или межсетевой экран блокирует TCP/UDP 33445 |
| `dyappd info` работает на хосте, но не отвечает извне | `listen` оставлен loopback по умолчанию; задайте `listen = ["[::]:33445", "0.0.0.0:33445"]` |
| Записи отвечают `STATUS_FULL` | Узел ещё не доверяет ни одному пиру (`storage_trust_minutes` после запуска), хранилище достигло квоты или на диске меньше `min_free_mb` |
| `dyappd` завершается при запуске из-за каталога | Каталог хранилища недоступен на запись пользователю узла; исправьте права или `ReadWritePaths=` |
| `run as the owner of ...` | Запускайте команды от пользователя службы: `sudo -u dyappd dyappd ...` |
| `dyappd` завершается с `storage belongs to ...` | `storage.dir` привязан к другому `network.name`; верните то имя или используйте новый каталог |
| `dyappd info` не работает с узлом именованной сети | Клиент говорит в сети `network.name` своего конфига; запустите его с конфигом узла или добавьте `--network.name <имя>` |
| `dyappd` завершается с `has store format N, this dyappd knows up to M` | Более новый `dyappd` обновил этот файл; запустите ту версию или восстановите копию, сделанную до неё ([Обновления](#обновления)) |
| `dyappd` завершается с `has search index format N, this dyappd knows up to M` | Более новый `dyappd` перестроил поисковый индекс; запустите ту версию или удалите названный `profiles-idx-vN.db`: догоняющая синхронизация заполнит его снова |
| `dyappd` завершается с `search.lock: ...; another dyappd uses this search index` | Два узла делят один `storage.dir`; дайте каждому свой каталог |
| Предупреждение `not listening` или `no address could be opened` | Порт занят (другой `dyappd`?) или IPv6 выключен на хосте; поправьте `listen` |
| Ключ отклонён с подсказкой `chmod 600` | У файла ключа есть биты прав группы или остальных |
| Диск продолжает расти | Профили хранятся `limits.profile_ttl_days` после последнего запроса владельца; уменьшите его или квоты хранилищ |
